Before you begin

Injection is one of the oldest and most damaging kinds of weakness, and it is almost always fixed the same way: keep the command and the data apart. This module covers SQL injection, command injection and cross-site scripting.

Have Juice Shop ready. You do not need to be signed in.

1

Theory: injection and cross-site scripting

How injection works, its main kinds, and the practices that prevent it.

What injection is

Injection happens when data from a user is joined into a command for another system (a database, the operating system, a browser) in a way that lets the data change the command itself. The other system cannot tell which part was written by you and which part was typed by the user.

For example, this code builds a query by joining text:

query = "SELECT * FROM users WHERE email = '" + email + "'"

If the user types ' OR '1'='1 as their email, the query becomes ... WHERE email = '' OR '1'='1', which matches every user.

Kinds of injection

KindWhere the data ends upMain fix
SQL injectionA database queryParameterised queries (prepared statements)
NoSQL injectionA query object, for example in MongoDBValidate types; never pass request objects straight into a query
OS command injectionA shell commandAvoid the shell; pass arguments as a list
Cross-site scripting (XSS)A web page in another user's browserEncode output; use safe browser functions such as textContent

Recommended practices

  • Keep code and data separate. Use parameterised queries, so the database receives the query and the values separately. This is the main fix for SQL injection, and it also handles legitimate values such as O'Brien correctly.
  • Use your framework's safe features. ORMs and query builders parameterise for you, unless you use their "raw query" functions with joined text.
  • Do not run shell commands with user data. If you must run a program, use the function that takes a list of arguments (execFile, subprocess.run([...]), ProcessBuilder), never a single command string.
  • Validate input as well (Module 1), as a second layer.

Cross-site scripting (XSS)

XSS is injection into a web page. An attacker gets their script to run in another user's browser, where it can read the page, act as the user, or steal data.

  • Stored XSS: the script is saved, for example in a product review, and runs for everyone who views it.
  • Reflected XSS: the script is in a link, and the server copies it into the page.
  • DOM XSS: the browser's own script copies data, such as the search text, into the page unsafely.

Fixes: let your template engine encode output (and do not turn it off), use textContent rather than innerHTML in browser code, sanitise with a trusted library such as DOMPurify when you must allow some HTML, and add a Content-Security-Policy (Module 3) as a further layer.

How to spot it in a code review

  • A query built with +, string formatting or template strings, with any part from the request.
  • "Raw" query functions in an ORM.
  • innerHTML, outerHTML, document.write, eval, or a template's "unescaped" or "safe" marker used with user data.
  • exec, system, shell=True or cmd /c with user data.
Watch out

Escaping quotes by hand, or removing words like SELECT from input, is not a fix. Attackers know many ways round such filters. Use parameters.

Fixes: parameters and safe output

The same lookup with the weakness and fixed, in each language, and the browser fix for DOM XSS.

The server-side examples look up a user by email address. The fix in every language is a parameterised query: the query text has a placeholder, and the value is sent separately. The browser example shows the matching fix for DOM XSS.

Node.js

The pg library for PostgreSQL. $1 is a placeholder for the first value.

With the weakness

const result = await pool.query(
  "SELECT id, name FROM users WHERE email = '" + req.body.email + "'"
);

Fixed

const result = await pool.query(
  "SELECT id, name FROM users WHERE email = $1",
  [req.body.email]                  // sent separately from the query
);
JavaScript (browser)

DOM XSS: the search text is written into the page as HTML.

With the weakness

const q = new URLSearchParams(location.search).get("q");
results.innerHTML = "You searched for: " + q;   // q can contain <img onerror=...>

Fixed

const q = new URLSearchParams(location.search).get("q");
results.textContent = "You searched for: " + q; // shown as text, never run
TypeScript

The same with a query builder. Template strings are still joined text unless the library treats them as parameters.

With the weakness

const rows = await db.raw(`SELECT id, name FROM users WHERE email = '${email}'`);

Fixed

const rows = await db("users").select("id", "name").where({ email });   // parameterised
// or, with raw SQL:
const rows2 = await db.raw("SELECT id, name FROM users WHERE email = ?", [email]);
Python

sqlite3 and most other database drivers take the values as a separate argument.

With the weakness

cur.execute(f"SELECT id, name FROM users WHERE email = '{email}'")
subprocess.run(f"ping -c 1 {host}", shell=True)           # command injection

Fixed

cur.execute("SELECT id, name FROM users WHERE email = ?", (email,))
subprocess.run(["ping", "-c", "1", host], check=True)    # no shell, argument list
Java

JDBC PreparedStatement. JPA and Spring Data parameterise for you, except in native queries built with joined text.

With the weakness

Statement st = conn.createStatement();
ResultSet rs = st.executeQuery(
    "SELECT id, name FROM users WHERE email = '" + email + "'");

Fixed

PreparedStatement ps = conn.prepareStatement(
    "SELECT id, name FROM users WHERE email = ?");
ps.setString(1, email);
ResultSet rs = ps.executeQuery();
C#

ADO.NET parameters. Entity Framework Core is safe with LINQ and with FromSql, but not with FromSqlRaw and joined text.

With the weakness

var cmd = new SqlCommand(
    "SELECT Id, Name FROM Users WHERE Email = '" + email + "'", conn);

Fixed

var cmd = new SqlCommand("SELECT Id, Name FROM Users WHERE Email = @email", conn);
cmd.Parameters.AddWithValue("@email", email);

// Entity Framework Core
var users = db.Users.Where(u => u.Email == email).ToList();
Recommended practice
  • Use parameters for every value, even ones you think are safe, such as numbers from your own code.
  • Table and column names cannot be parameters. If they must vary, pick them from a fixed allow-list in your code.
  • Give the database account only the rights it needs (Module 1, least privilege), so a successful injection can do less.

    "alice@example.com",
    "o'brien@example.com",
    "' OR '1'='1",

Java

This starter uses the H2 in-memory database. Download h2-2.2.224.jar from Maven Central into the same folder.

FindUser.java

import java.sql.*;

public class FindUser {
    // TODO: use a PreparedStatement with a ? parameter
    static int findUser(Connection db, String email) throws SQLException {
        try (Statement st = db.createStatement();
             ResultSet rs = st.executeQuery("SELECT email, name FROM users WHERE email = '" + email + "'")) {
            int n = 0;
            while (rs.next()) n++;
            return n;
        }
    }

    public static void main(String[] args) throws Exception {
        try (Connection db = DriverManager.getConnection("jdbc:h2:mem:lab")) {
            try (Statement st = db.createStatement()) {
                st.execute("CREATE TABLE users (email VARCHAR(100), name VARCHAR(100), role VARCHAR(20))");
                st.execute("INSERT INTO users VALUES ('alice@example.com', 'Alice', 'admin'), "
                         + "('o''brien@example.com', 'Pat O''Brien', 'customer')");
            }
            String[] inputs = {
                "alice@example.com",
                "o'brien@example.com",
                "' OR '1'='1",
                "x' UNION SELECT email, role FROM users --"
            };
            for (int i = 0; i < inputs.length; i++) {
                try {
                    System.out.println((i + 1) + " " + findUser(db, inputs[i]) + " row(s)");
                } catch (SQLException e) {
                    System.out.println((i + 1) + " error: " + e.getMessage().split("\n")[0]);
                }
            }
        }
    }
}

Before you begin

Broken access control is the most common serious weakness in web applications. This module covers checking permissions and record ownership on the server, and server-side request forgery, which OWASP now counts in the same category.

Theory: access control and SSRF

How access control breaks, the practices that prevent it, and how SSRF works.

What access control is

Authentication answers "who are you?". Access control (also called authorisation) answers "are you allowed to do this, to this record, right now?". Broken access control means a user can read or change data, or use functions, that should not be open to them.

Common ways it breaks

  • Changing an ID. A user changes /orders/1001 to /orders/1002 and sees someone else's order. This is called an insecure direct object reference (IDOR).
  • Hidden is not protected. An admin page is missing from the menu, but anyone who types its address can use it.
  • Trusting the client. The user's role or user ID is read from a hidden form field, a cookie the user can edit, or the request body.
  • Missing checks on some methods. GET is checked, but PUT and DELETE on the same address are not.
  • Overly open CORS. The API tells browsers that any website may call it with the user's cookies.

Recommended practices

  • Deny by default. Every endpoint is closed unless a rule opens it.
  • Check on the server, on every request. Use one shared check (middleware, a policy or an attribute) rather than a check copied into each handler.
  • Check ownership of the record, not only the role. Look the record up by its ID and the signed-in user, so another user's record is simply not found.
  • Take the user's identity from the session or verified token, never from the request body or URL.
  • Return 404 rather than 403 for records the user does not own, so attackers cannot tell which IDs exist.
  • Log access-control failures and alert when one user produces many of them.

Server-side request forgery (SSRF)

SSRF happens when your server fetches a URL that the user supplied, for example to show a link preview or import an image. An attacker gives an address that only your server can reach, such as an internal admin service, or the cloud metadata address 169.254.169.254, which can hand out temporary cloud credentials.

  • Allow-list the destinations. Accept only https URLs to a fixed list of host names, on the default port.
  • Parse the URL with a proper URL library and compare the parsed host exactly. Never use "contains" or "starts with" on the URL text.
  • Block private and internal addresses after the name is resolved to an IP address, and do not follow redirects to other hosts.
  • Use the network as well. Send outbound fetches through a proxy or firewall that only allows the hosts you need. On AWS, require IMDSv2 for the metadata service.

Where these weaknesses sit in the OWASP Top 10:2025, with their CWE numbers.

This module maps to A01:2025 Broken Access Control, the highest-ranked category in the list. In the 2025 edition, server-side request forgery is part of A01 instead of being a separate category.

How to spot it in a code review

  • A database lookup by ID that does not also filter by the signed-in user or check the result's owner.
  • A user ID, role or price read from the request body or a query parameter.
  • A route registered without the shared authorisation middleware or attribute.
  • Any call that fetches a URL, where part of the URL came from the request.
Watch out

Using random IDs such as UUIDs instead of 1, 2, 3 makes IDs harder to guess, but it is not access control. IDs leak through links, logs and browser history. The ownership check is still needed.

Fixes: check ownership on the server

The same order endpoint with the weakness and fixed, in each language.

The example is an endpoint that returns one order: GET /api/orders/{id}. The rule is that a signed-in user can see only their own orders. The fix in every language is to look the order up by its ID and the signed-in user's ID, so another user's order is not found.

Node.js

Express. The user ID comes from the verified session, never from the request.

With the weakness

app.get("/api/orders/:id", requireLogin, async (req, res) => {
  const order = await db.orders.findOne({ id: req.params.id });   // any order
  if (!order) return res.sendStatus(404);
  res.json(order);
});

Fixed

app.get("/api/orders/:id", requireLogin, async (req, res) => {
  const order = await db.orders.findOne({
    id: req.params.id,
    ownerId: req.session.userId,          // only this user's orders
  });
  if (!order) return res.sendStatus(404); // same answer whether it exists or not
  res.json(order);
});
JavaScript (browser)

Hiding a button in the browser does not protect the action behind it.

With the weakness

// The admin link is only shown to admins, so the developer skips the server check
if (currentUser.role === "admin") {
  menu.append(adminLink);                 // the API behind it is still open
}

Fixed

// Hiding the link is fine for the user interface...
if (currentUser.role === "admin") menu.append(adminLink);

// ...but the server must refuse the call for everyone else.
const res = await fetch("/api/admin/users");
if (res.status === 403) showMessage("You do not have access to this page.");
TypeScript

The same ownership rule, written once as a helper so every handler uses it.

With the weakness

app.get("/api/orders/:id", requireLogin, async (req: Request, res: Response) => {
  const order = await orders.findById(req.params.id);   // no owner check
  res.json(order);
});

Fixed

async function findOwnedOrder(id: string, userId: string): Promise<Order | null> {
  return orders.findOne({ id, ownerId: userId });
}

app.get("/api/orders/:id", requireLogin, async (req: Request, res: Response) => {
  const order = await findOwnedOrder(req.params.id, req.session.userId);
  if (!order) return res.sendStatus(404);
  res.json(order);
});
Python

FastAPI. The current user comes from a dependency that checks the session or token.

With the weakness

@app.get("/api/orders/{order_id}")
def get_order(order_id: int, user: User = Depends(current_user)):
    return db.get(Order, order_id)        # any order, whoever owns it

Fixed

@app.get("/api/orders/{order_id}")
def get_order(order_id: int, user: User = Depends(current_user)):
    order = db.scalar(
        select(Order).where(Order.id == order_id, Order.owner_id == user.id)
    )
    if order is None:
        raise HTTPException(status_code=404)
    return order
Java

Spring Boot with Spring Data. The repository method filters by owner.

With the weakness

@GetMapping("/api/orders/{id}")
public Order get(@PathVariable long id) {
    return orders.findById(id).orElseThrow(NotFound::new);   // any order
}

Fixed

// In OrderRepository:
Optional<Order> findByIdAndOwnerId(long id, String ownerId);

@GetMapping("/api/orders/{id}")
public Order get(@PathVariable long id, Principal user) {
    return orders.findByIdAndOwnerId(id, user.getName())
                 .orElseThrow(NotFound::new);                  // 404 for others' orders
}
C#

ASP.NET Core with Entity Framework Core.

With the weakness

[Authorize]
[HttpGet("api/orders/{id}")]
public async Task<IActionResult> Get(int id)
{
    var order = await _db.Orders.FindAsync(id);    // any order
    return order is null ? NotFound() : Ok(order);
}

Fixed

[Authorize]
[HttpGet("api/orders/{id}")]
public async Task<IActionResult> Get(int id)
{
    var userId = User.FindFirstValue(ClaimTypes.NameIdentifier);
    var order = await _db.Orders
        .SingleOrDefaultAsync(o => o.Id == id && o.OwnerId == userId);
    return order is null ? NotFound() : Ok(order);
}
Recommended practice
  • Put the ownership rule in one place (a repository method, a policy, or a helper) and use it everywhere.
  • Write a test that signs in as user A and asks for user B's record. It must fail.
  • For URL fetching, check the parsed URL against an allow-list before the request is made. Part B of the lab practises this.

Lab: open another user's basket, then block bad URLs

Part A: the View Basket challenge in Juice Shop. Part B: an allow-list check for outbound URLs.

Part A: open another user's basket in Juice Shop

Start Juice Shop on 127.0.0.1 and sign in with the account you made in Module 1.

  1. Open your basket. Juice Shop loads it using a basket number kept in the browser.
  2. Open the developer tools (F12), go to Application (Chrome or Edge) or Storage (Firefox), then Session storage for http://localhost:3000. Find the key bid. Its value is your basket number.
  3. Change bid to a different number, such as 1, and reload the basket page.

You now see another user's basket, and Juice Shop shows a banner for the View Basket challenge. The server returned the basket without checking that it belongs to you.

Think about it

Which line of server code would you change? The fix is the ownership check from Section 3: look the basket up by its number and the signed-in user.

Before you begin

If an attacker can sign in as someone else, every other control is bypassed. This module covers password rules, limits on guessing, multi-factor authentication, session cookies and JSON Web Tokens.

This is the last module before the final test. Have Juice Shop ready.

1

Theory: passwords, sign-in and sessions

Current password rules, stopping guessing attacks, and keeping sessions and tokens safe.

Passwords

NIST SP 800-63B (revision 4, 2025) sets these rules for passwords:

  • At least 15 characters when the password is the only factor, and at least 8 when it is used with multi-factor authentication.
  • Allow at least 64 characters, and allow spaces and all characters, so people can use passphrases.
  • No composition rules such as "must contain a symbol", and no forced changes every few months. Ask for a change only when there is a sign the password was leaked.
  • Check new passwords against lists of breached and common passwords, such as admin123 or Password1.
  • Store passwords with a slow, salted hash (Module 4).

Stopping guessing attacks

  • Credential stuffing: attackers try username and password pairs leaked from other sites. Brute force: they try many passwords for one account.
  • Limit failed attempts per account and per source, with growing delays or a temporary block. NIST sets an upper limit of 100 failures in a row before an account must be locked.
  • Offer multi-factor authentication (MFA), and require it for admin accounts. Prefer app-based codes, security keys or passkeys over SMS.
  • Give the same message for "no such user" and "wrong password", so attackers cannot find out which accounts exist.

Sessions

After sign-in, a session remembers who the user is, usually through a cookie that holds a random session ID.

PracticeWhy
Create a new session ID when the user signs inStops session fixation, where an attacker plants a known session ID before the user signs in.
Set the cookie flags HttpOnly, Secure and SameSite=Lax (or Strict)Scripts cannot read the cookie, it is only sent over HTTPS, and other sites cannot easily send it with their requests.
End sessions on the server at sign-out, and after a period of no activityA stolen session ID stops working.
Do not put session IDs or tokens in URLs or browser storageURLs end up in logs and browser history, and any script on the page can read localStorage.

JSON Web Tokens (JWT)

  • Check the signature on every request, and allow only the algorithm you expect. Never accept alg: none.
  • Set a short expiry (exp) and check it, and check the issuer and audience.
  • Do not put secrets or personal data in a JWT. Its contents are only encoded, as you saw in Module 4.

Watch out

Cookie flags and session handling are often set once in a shared configuration file and never checked again. Review them whenever the framework or hosting changes.

Fixes: cookie flags, new sessions and token checks

A sign-in flow with the weakness and fixed, in each language.

The examples show a sign-in flow. The fix in every language: secure cookie flags, a short session lifetime, a new session at sign-in, one message for every failed sign-in, and a limit on attempts. The TypeScript block shows how to check a JWT properly.

Node.js

Express with express-session.

With the weakness

app.use(session({ secret: "keyboard cat" }));     // default cookie settings

app.post("/login", async (req, res) => {
  const user = await checkPassword(req.body.email, req.body.password);
  if (!user) return res.status(401).send("Wrong password for " + req.body.email);
  req.session.userId = user.id;                     // same session ID as before sign-in
  res.redirect("/");
});

Fixed

app.use(session({
  secret: process.env.SESSION_SECRET,               // from a secret store, not the code
  cookie: { httpOnly: true, secure: true, sameSite: "lax", maxAge: 30 * 60 * 1000 },
}));

app.post("/login", loginLimiter, async (req, res, next) => {
  const user = await checkPassword(req.body.email, req.body.password);
  if (!user) return res.status(401).send("Email or password is incorrect");
  req.session.regenerate((err) => {                 // new session ID at sign-in
    if (err) return next(err);
    req.session.userId = user.id;
    res.redirect("/");
  });
});
JavaScript (browser)

Where the browser keeps the sign-in token matters.

With the weakness

// Any script on the page, including injected ones, can read this
localStorage.setItem("token", data.token);

Fixed

// The server sets the session cookie with HttpOnly, so scripts cannot read it.
// The browser sends it automatically:
await fetch("/api/profile", { credentials: "same-origin" });
TypeScript

Checking a JWT with the jose library: expected algorithm, issuer, audience and expiry.

With the weakness

const payload = JSON.parse(Buffer.from(token.split(".")[1], "base64url").toString());
// the signature is never checked

Fixed

import { jwtVerify } from "jose";

const { payload } = await jwtVerify(token, publicKey, {
  algorithms: ["RS256"],            // only the algorithm you use
  issuer: "https://login.example.com",
  audience: "shop-api",
});                                 // also rejects expired tokens
Python

Flask. Set the cookie flags in the app settings and clear the old session at sign-in.

With the weakness

app.config["SESSION_COOKIE_SECURE"] = False

@app.post("/login")
def login():
    user = check_password(request.form["email"], request.form["password"])
    session["user_id"] = user.id

Fixed

app.config.update(
    SESSION_COOKIE_HTTPONLY=True,
    SESSION_COOKIE_SECURE=True,
    SESSION_COOKIE_SAMESITE="Lax",
    PERMANENT_SESSION_LIFETIME=timedelta(minutes=30),
)

@app.post("/login")
def login():
    user = check_password(request.form["email"], request.form["password"])
    if user is None:
        abort(401, "Email or password is incorrect")
    session.clear()                  # start a fresh session at sign-in
    session["user_id"] = user.id

C#

ASP.NET Core cookie authentication.

With the weakness

builder.Services.AddAuthentication(CookieAuthenticationDefaults.AuthenticationScheme)
    .AddCookie(o => o.ExpireTimeSpan = TimeSpan.FromDays(30));

Fixed

builder.Services.AddAuthentication(CookieAuthenticationDefaults.AuthenticationScheme)
    .AddCookie(o =>
    {
        o.Cookie.HttpOnly = true;
        o.Cookie.SecurePolicy = CookieSecurePolicy.Always;
        o.Cookie.SameSite = SameSiteMode.Lax;
        o.ExpireTimeSpan = TimeSpan.FromMinutes(30);
        o.SlidingExpiration = true;
    });
// Also add a rate limiter (builder.Services.AddRateLimiter) to POST /login
Recommended practice
  • Use your framework's built-in sign-in and session features, or a trusted identity provider, rather than writing your own.
  • Apply rate limits to every place a password or code is checked: sign-in, password reset and MFA codes.
  • Log failed sign-ins, and alert on many failures for one account or from one source.

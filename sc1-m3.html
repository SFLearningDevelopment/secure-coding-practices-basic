Before you begin

Many breaches start with a setting, not a bug. This module covers the settings to check in your framework, web server and cloud services, and the security headers every response should carry.

1

Theory: secure settings and headers

The most common unsafe settings, the main security headers, and how to keep settings safe.

Security misconfiguration means the code may be fine, but the way the app, framework, server or cloud service is set up leaves a gap. It is common because every layer has its own settings, and many defaults are chosen for ease of use, not safety.

Common misconfigurations

  • Detailed error pages in production. Stack traces show file paths, library versions, SQL and sometimes secrets.
  • Debug features left on, such as debug mode, admin consoles, sample apps and test endpoints.
  • Default accounts and passwords that were never changed.
  • Directory listing turned on, so anyone can browse and download files in a folder.
  • Missing security headers that tell browsers how to protect users.
  • Revealing version numbers in headers such as Server or X-Powered-By, which tells attackers which known weaknesses to try.
  • CORS open to every website together with cookies or credentials.
  • Cloud storage open to the public, such as an S3 bucket that anyone can list.

Security headers

HeaderExample valueWhat it does
Content-Security-Policydefault-src 'self'; frame-ancestors 'none'Lets the browser load scripts, styles and images only from the places you list, and stops other sites from framing your pages. It limits the damage of cross-site scripting (Module 5).
Strict-Transport-Securitymax-age=31536000; includeSubDomainsTells the browser to use HTTPS only for this site for a year. Browsers apply it only when it arrives over HTTPS.
X-Content-Type-OptionsnosniffStops the browser from guessing a file's type, so an uploaded text file is not run as a script.
Referrer-Policyno-referrer or strict-origin-when-cross-originLimits how much of your page address is sent to other sites when users follow a link.

Recommended practices

  • Harden by default. Start from a minimal setup and turn on only what is needed. Remove sample apps, unused features and unused ports.
  • Same settings everywhere. Keep development, test and production set up the same way, from configuration stored in Git, so a fix is not lost in one environment.
  • Show users a general error message. Log the details on the server, with an ID the user can quote to support.
  • Add the security headers to every response, in one place such as middleware.
  • Check your settings automatically, with tools such as a header scanner in the build pipeline or Prowler for cloud accounts.

OWASP mapping

Where these weaknesses sit in the OWASP Top 10:2025, with their CWE numbers.

This module maps to A02:2025 Security Misconfiguration, which moved up from fifth place in 2021 to second place in 2025.

WeaknessCWEOWASP Top 10:2025

Files can be browsed through a directory listingCWE-548: Exposure of Information Through Directory ListingA02 Security Misconfiguration
Debug code or features are left on in productionCWE-489: Active Debug CodeA02 Security Misconfiguration

Where to look

  • Framework settings: debug mode, error pages, CORS, cookie settings.
  • Web server or reverse proxy: directory listing, version headers, TLS settings.
  • Container images: running as root, extra tools left in the image.
  • Cloud services: public buckets, open security groups, logging turned off.
Watch out

A setting fixed by hand on one server is lost when the server is rebuilt. Fix it in the configuration that is stored in Git, so every environment gets it.

Fixes: errors, version headers and security headers

Settings with the weakness and fixed, in each language.

The example is the same in each language: turn off detailed errors for users, stop announcing the server and its version, and add the security headers to every response.

Node.js

Express with the helmet package (npm install helmet), which sets the security headers.

With the weakness

const app = express();               // sends "X-Powered-By: Express"

app.use((err, req, res, next) => {
  res.status(500).send(err.stack);   // stack trace goes to the user
});

Fixed

import helmet from "helmet";

const app = express();
app.disable("x-powered-by");
app.use(helmet({
  contentSecurityPolicy: { directives: { defaultSrc: ["'self'"], frameAncestors: ["'none'"] } },
  referrerPolicy: { policy: "no-referrer" },
}));

app.use((err, req, res, next) => {
  const id = crypto.randomUUID();
  console.error(id, err);            // details stay in the server log
  res.status(500).json({ error: "Something went wrong", id });
});
JavaScript (browser)

With a Content-Security-Policy of script-src 'self', the browser refuses inline scripts. Move the script to a file.

Blocked by the policy

<button onclick="buy()">Buy</button>
<script>
  function buy() { /* ... */ }
</script>

Fixed

<!-- buy.js is served from your own site, so the policy allows it -->
<button id="buy">Buy</button>
<script src="/js/buy.js"></script>

// buy.js
document.getElementById("buy").addEventListener("click", buy);
TypeScript

Express with helmet, and a typed error handler.

With the weakness

app.use((err: Error, req: Request, res: Response, next: NextFunction) => {
  res.status(500).json({ message: err.message, stack: err.stack });
});

Fixed

app.disable("x-powered-by");
app.use(helmet());

app.use((err: Error, req: Request, res: Response, _next: NextFunction) => {
  const id = randomUUID();
  logger.error({ id, err });
  res.status(500).json({ error: "Something went wrong", id });
});
Python

FastAPI. Keep debug off and add the headers in middleware.

With the weakness

app = FastAPI(debug=True)            # shows tracebacks in responses

Fixed

app = FastAPI(debug=False, docs_url=None, redoc_url=None)   # no public API docs in production

SECURITY_HEADERS = {
    "Content-Security-Policy": "default-src 'self'; frame-ancestors 'none'",
    "Strict-Transport-Security": "max-age=31536000; includeSubDomains",
    "X-Content-Type-Options": "nosniff",
    "Referrer-Policy": "no-referrer",
}

@app.middleware("http")
async def add_security_headers(request, call_next):
    response = await call_next(request)
    response.headers.update(SECURITY_HEADERS)
    return response
Java

Spring Boot with Spring Security, which adds several headers by default.

With the weakness

# application.properties
server.error.include-stacktrace=always
server.error.include-message=always

Fixed

# application.properties
server.error.include-stacktrace=never
server.error.include-message=never
server.server-header=

// SecurityConfig.java
http.headers(h -> h
    .contentSecurityPolicy(c -> c.policyDirectives("default-src 'self'; frame-ancestors 'none'"))
    .referrerPolicy(r -> r.policy(ReferrerPolicy.NO_REFERRER)));
C#

ASP.NET Core. The developer error page must only run in Development.

With the weakness

var app = builder.Build();
app.UseDeveloperExceptionPage();     // in every environment

Fixed

builder.WebHost.ConfigureKestrel(o => o.AddServerHeader = false);
var app = builder.Build();

if (!app.Environment.IsDevelopment())
{
    app.UseExceptionHandler("/error");   // general message, details logged
    app.UseHsts();
}
app.Use(async (ctx, next) =>
{
    ctx.Response.Headers["Content-Security-Policy"] = "default-src 'self'; frame-ancestors 'none'";
    ctx.Response.Headers["X-Content-Type-Options"] = "nosniff";
    ctx.Response.Headers["Referrer-Policy"] = "no-referrer";
    await next();
});
Recommended practice
  • Set headers and error handling once, in middleware or framework settings, not in each handler.
  • Give each error an ID that is shown to the user and written to the log, so support can find the details.
  • Check the result from outside with curl -I or the browser's Network tab.

Part B: harden a small web server

Each starter is a tiny web server with two addresses: / returns "Hello", and /boom fails on purpose with an error message that contains a secret detail. Change the starter so that:

  1. Every response has these four headers:
Content-Security-Policy: default-src 'self'; frame-ancestors 'none'
Strict-Transport-Security: max-age=31536000; includeSubDomains
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
  1. /boom returns status 500 with the text Something went wrong. The details are written to the server's own log or console instead.
  2. No Server or X-Powered-By header shows a product version.

Java

Server.java

import com.sun.net.httpserver.HttpExchange;
import com.sun.net.httpserver.HttpServer;
import java.io.IOException;
import java.io.PrintWriter;
import java.io.StringWriter;
import java.net.InetSocketAddress;
import java.nio.charset.StandardCharsets;

public class Server {
    // TODO: add the four security headers to every response
    static void send(HttpExchange ex, int status, String text) throws IOException {
        byte[] body = text.getBytes(StandardCharsets.UTF_8);
        ex.getResponseHeaders().set("Content-Type", "text/plain");
        ex.sendResponseHeaders(status, body.length);
        ex.getResponseBody().write(body);
        ex.close();
    }

    public static void main(String[] args) throws IOException {
        HttpServer server = HttpServer.create(new InetSocketAddress("127.0.0.1", 8080), 0);
        server.createContext("/", ex -> {
            try {
                if (ex.getRequestURI().getPath().equals("/boom"))
                    throw new IllegalStateException("Database password rejected for user app_admin");
                send(ex, 200, "Hello\n");
            } catch (Exception e) {
                // TODO: log the details on the server and send a general message instead
                StringWriter sw = new StringWriter();
                e.printStackTrace(new PrintWriter(sw));
                send(ex, 500, sw.toString());
            }
        });
        server.start();
        System.out.println("http://127.0.0.1:8080");
    }
}

Good to know

Some servers print header names in a different letter case, such as X-content-type-options. Header names are not case-sensitive, so this is fine.

Before you begin

Most of the weaknesses in this course come from the same few mistakes: trusting data that came from outside, giving code more access than it needs, and not deciding what should happen when something goes wrong. This module covers the principles that prevent those mistakes.

Have Juice Shop ready to start, as set up in Module 0, and the tools for at least one language.

1

Theory: secure design principles

Where security fits in development, the principles to design with, and how to treat input and output.

Security in every stage of development

A secure development lifecycle means security work happens in every stage, not only in a test at the end. Weaknesses found early are cheaper and easier to fix.

StageSecurity work
RequirementsWrite down what must be protected and who may do what. For example: "Only the basket's owner can change it."
DesignList what could go wrong and how the design prevents it (threat modelling, covered in Course 2).
CodeFollow secure coding guidelines like the ones in this course. Use well-known libraries instead of writing your own security code.
Review and testCode review with security in mind, automatic code scanning, and testing the running app.
Release and runSecure settings, logging and alerts, and a way to patch quickly.

Principles to design with

  • Least privilege. Give each user, service and database account only the access it needs for its job, and nothing more. If it is misused, the damage is limited.
  • Secure defaults. The out-of-the-box setting should be the safe one. For example, new accounts have no admin rights, and debug pages are off.
  • Fail safely. When something goes wrong, the result should be the safe outcome. If a permission check throws an error, the answer is "no", not "yes".
  • Several layers of protection. Do not rely on one control. If input checks miss something, parameterised database queries still stop SQL injection.
  • Small attack surface. Every page, endpoint, open port and feature is something an attacker can try. Remove what is not needed.
  • Do not trust input. Treat everything from outside your server as possibly hostile until it is checked.

Trust boundaries

A trust boundary is any point where data moves from something you do not control to something you do. The most important one is between the browser and your server. Data also crosses a trust boundary when it comes from a file upload, another company's API, a message queue or a request header.

Check input: allow-lists, on the server

  • Check on the server. Checks in the browser make forms friendlier, but they protect nothing, because the user controls the browser.
  • Use an allow-list. Say exactly what is acceptable (type, length, range, format, or a fixed list of values) and reject everything else. A deny-list of "bad" values always misses some.
  • Check the type strictly. The text "2" is not the number 2, and 2.5 is not a whole number. Some libraries convert these quietly unless you tell them not to.
  • Reject unknown fields. If the request has a field you did not ask for, such as price, reject it rather than ignore it.
  • Reject, do not repair. If a value is wrong, send an error (status 400). Do not try to "clean" it and carry on.

Encode output for where it goes

Checking input is not enough on its own, because a value can be valid and still be dangerous in a particular place. A name such as O'Brien <Ltd> is a valid name, but it can break HTML or a query if it is pasted in as plain text. Encode each value for the place where it is used:

Where the value goesWhat to do
A web page (HTML)HTML-encode it. Most template engines do this by default. Do not turn that off.
A URLURL-encode it, for example with encodeURIComponent.
A database queryPass it as a parameter. Never join it into the query text (Module 5).
A shell commandAvoid the shell. Pass arguments as a list to the program you run.
Good to know

Checking input and encoding output work together. Checking stops values that make no sense for the business. Encoding makes sure even valid values cannot change the meaning of a page or query.

OWASP mapping

Which OWASP Top 10:2025 category these weaknesses belong to, and their CWE numbers.

This module maps mainly to A06:2025 Insecure Design. Insecure design means a security control is missing or weak because it was never planned, not because it was coded badly. A design that trusts the browser to check the basket quantity is insecure, however carefully that design is coded.

WeaknessCWEOWASP Top 10:2025
A security check runs only in the browserCWE-602: Client-Side Enforcement of Server-Side SecurityA06 Insecure Design
Input is used without checking its type, range or formatCWE-20: Improper Input ValidationA06 Insecure Design; it is also the starting point for A05 Injection
Output is not encoded for where it is usedCWE-116: Improper Encoding or Escaping of OutputA05 Injection (cross-site scripting in Module 5)

Insecure design compared with insecure code

  • Insecure design: the basket service was never designed to check quantities. The fix is to add the missing control.
  • Insecure code: the design says "check quantities", but the code checks quantity > 10 and forgets negative numbers. The fix is to correct the code.

Both lead to the same attack, but they are fixed in different places. A design review asks "which checks must exist?" A code review asks "is each check correct?"

Watch out

A check that exists but can be skipped counts as missing. If a value is checked on one endpoint but another endpoint accepts it unchecked, an attacker will use the second endpoint.

3

Fixes: validate on the server

The same basket endpoint with the weakness and fixed, in each language.

The example is an endpoint that adds an item to a shopping basket. It receives a JSON body such as {"productId": 1, "quantity": 2}. The business rule is: the product number is a positive whole number, the quantity is a whole number from 1 to 10, and no other fields are allowed.

The recommended fix is the same in every language. Describe the allowed shape of the request once, check every request against it on the server, reject anything that does not match, and use only the checked values afterwards.

Node.js

Express with the zod library (npm install zod).

With the weakness

app.post("/api/basket/items", async (req, res) => {
  const { productId, quantity } = req.body;   // used exactly as sent
  await basket.add(req.user.id, productId, quantity);
  res.status(201).end();
});

Fixed

import { z } from "zod";

const AddItem = z.object({
  productId: z.number().int().positive(),
  quantity: z.number().int().min(1).max(10),
}).strict();                      // reject unknown fields

app.post("/api/basket/items", async (req, res) => {
  const parsed = AddItem.safeParse(req.body);
  if (!parsed.success) {
    return res.status(400).json({ error: "Invalid basket item" });
  }
  const { productId, quantity } = parsed.data;  // checked values only
  await basket.add(req.user.id, productId, quantity);
  res.status(201).end();
});
JavaScript (browser)

A check in the browser helps the user, but it is not a security control.

Check in the browser only

// The form only allows 1 to 10, so the developer assumes the server is safe
qtyInput.min = 1;
qtyInput.max = 10;
if (qty < 1 || qty > 10) { showError("Choose 1 to 10"); return; }
await fetch("/api/basket/items", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ productId, quantity: qty }),
});

How it is bypassed

// Anyone can type this into the browser console. It never touches the form,
// so the check above never runs. Only a check on the server stops it.
fetch("/api/basket/items", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ productId: 1, quantity: -100 }),
});
TypeScript

TypeScript types are removed when the code is compiled, so they do not check anything at run time. Validate with zod, and take the type from the schema.

With the weakness

interface AddItem { productId: number; quantity: number; }

app.post("/api/basket/items", async (req, res) => {
  const item = req.body as AddItem;   // "as" checks nothing at run time
  await basket.add(req.user.id, item.productId, item.quantity);
  res.status(201).end();
});

Fixed

import { z } from "zod";

const AddItem = z.object({
  productId: z.number().int().positive(),
  quantity: z.number().int().min(1).max(10),
}).strict();
type AddItem = z.infer<typeof AddItem>;  // the type comes from the checked schema

app.post("/api/basket/items", async (req, res) => {
  const parsed = AddItem.safeParse(req.body);
  if (!parsed.success) {
    return res.status(400).json({ error: "Invalid basket item" });
  }
  const item: AddItem = parsed.data;
  await basket.add(req.user.id, item.productId, item.quantity);
  res.status(201).end();
});
Python

FastAPI with pydantic. FastAPI rejects a request that does not match the model with status 422.

With the weakness

@app.post("/api/basket/items", status_code=201)
async def add_item(request: Request):
    body = await request.json()            # used exactly as sent
    await basket.add(request.state.user_id, body["productId"], body["quantity"])

Fixed

from pydantic import BaseModel, ConfigDict, Field

class AddItem(BaseModel):
    # strict: "2" is not accepted as the number 2. forbid: no extra fields.
    model_config = ConfigDict(strict=True, extra="forbid")
    productId: int = Field(gt=0)
    quantity: int = Field(ge=1, le=10)

@app.post("/api/basket/items", status_code=201)
async def add_item(item: AddItem, request: Request):
    await basket.add(request.state.user_id, item.productId, item.quantity)
Java

Spring Boot with Jakarta Bean Validation (spring-boot-starter-validation). @Valid makes Spring reject a request that breaks a rule with status 400.

With the weakness

public record AddItem(long productId, int quantity) {}

@PostMapping("/api/basket/items")
public ResponseEntity<Void> add(@RequestBody AddItem item, Principal user) {
    basket.add(user.getName(), item.productId(), item.quantity());
    return ResponseEntity.status(201).build();
}

Fixed

import jakarta.validation.Valid;
import jakarta.validation.constraints.*;

public record AddItem(
    @Positive long productId,
    @Min(1) @Max(10) int quantity) {}

@PostMapping("/api/basket/items")
public ResponseEntity<Void> add(@Valid @RequestBody AddItem item, Principal user) {
    basket.add(user.getName(), item.productId(), item.quantity());
    return ResponseEntity.status(201).build();
}

// application.properties: also reject fields that are not in AddItem
// spring.jackson.deserialization.fail-on-unknown-properties=true
C#

ASP.NET Core with data annotations. With [ApiController], a request that breaks a rule is rejected with status 400 before your code runs.

With the weakness

public record AddItem(long ProductId, int Quantity);

[ApiController]
[Route("api/basket/items")]
public class BasketController : ControllerBase
{
    [HttpPost]
    public async Task<IActionResult> Add(AddItem item)
    {
        await _basket.AddAsync(User.Identity!.Name!, item.ProductId, item.Quantity);
        return StatusCode(201);
    }
}

Fixed

using System.ComponentModel.DataAnnotations;

public record AddItem(
    [Range(1, int.MaxValue)] long ProductId,
    [Range(1, 10)] int Quantity);

[ApiController]                       // rejects an invalid AddItem with 400
[Route("api/basket/items")]
public class BasketController : ControllerBase
{
    [HttpPost]
    public async Task<IActionResult> Add(AddItem item)
    {
        await _basket.AddAsync(User.Identity!.Name!, item.ProductId, item.Quantity);
        return StatusCode(201);
    }
}
Recommended practice
  • Use your framework's validation library rather than writing checks by hand in every handler.
  • Turn on strict type checks and reject unknown fields.
  • Return a short, general error message. Do not echo the bad value or show a stack trace.

Lab: get past a browser-only check, then fix it

Part A: buy a negative quantity in Juice Shop. Part B: write the server-side check in your language.

Part A: exploit the weakness in Juice Shop

Start Juice Shop as in Module 0 (on 127.0.0.1 only) and open http://localhost:3000.

  1. Create an account with a made-up email address, and sign in.
  2. Add any product to your basket. Open the basket and try to set the quantity below 1 with the buttons. The page does not allow it. That is the check in the browser.
  3. Open the developer tools (F12) and go to the Network tab. Change the quantity once with the buttons. Find the PUT request to /api/BasketItems/ followed by a number. That number is your basket item's ID.
  4. Go to the Console tab and send the request yourself, with your item ID in place of ITEM_ID:
const token = localStorage.getItem("token");
await fetch("/api/BasketItems/ITEM_ID", {
  method: "PUT",
  headers: { "Content-Type": "application/json", "Authorization": "Bearer " + token },
  body: JSON.stringify({ quantity: -100 }),
}).then(r => r.json());
  1. Reload the basket. The quantity is -100 and the total is negative.
  2. Go to checkout. Add a made-up address and a made-up card, and place the order.

Juice Shop shows a green banner saying you solved the Payback Time challenge. The server accepted a quantity that the page would never allow.

import com.fasterxml.jackson.databind.DeserializationFeature;
import com.fasterxml.jackson.databind.MapperFeature;
import com.fasterxml.jackson.databind.ObjectMapper;
import com.fasterxml.jackson.databind.json.JsonMapper;
import jakarta.validation.Validation;
import jakarta.validation.Validator;
import jakarta.validation.constraints.*;

public class ValidateDemo {
    // TODO: add the rules so that only input 1 is accepted
    public record AddItem(long productId, int quantity) {}

    public static void main(String[] args) {
        String[] inputs = {
            "{\"productId\": 1, \"quantity\": 2}",
            "{\"productId\": 1, \"quantity\": -100}",
            "{\"productId\": 1, \"quantity\": 0}",
            "{\"productId\": 1, \"quantity\": 11}",
            "{\"productId\": 1, \"quantity\": 2.5}",
            "{\"productId\": 1, \"quantity\": \"2\"}",
            "{\"productId\": 1}",
            "{\"productId\": 1, \"quantity\": 2, \"price\": 0}"
        };
        ObjectMapper mapper = JsonMapper.builder()
            .disable(MapperFeature.ALLOW_COERCION_OF_SCALARS)    // "2" is text, not a number
            .disable(DeserializationFeature.ACCEPT_FLOAT_AS_INT)  // 2.5 is not a whole number
            .enable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES)
            .build();
        Validator validator = Validation.buildDefaultValidatorFactory().getValidator();
        for (int i = 0; i < inputs.length; i++) {
            String result;
            try {
                AddItem item = mapper.readValue(inputs[i], AddItem.class);
                result = validator.validate(item).isEmpty() ? "accepted" : "rejected";
            } catch (Exception e) {
                result = "rejected";
            }
            System.out.println((i + 1) + " " + result);
        }
    }
}
